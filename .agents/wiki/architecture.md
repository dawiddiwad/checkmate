# Architecture

> **Agent only:** This file contains repository or workflow instructions for coding agents.

Checkmate includes a Claude Code plugin, a Pi package, and a deterministic Node.js toolkit. The workspace setting selects the host for new work. A CLI caller can override it with `CHECKMATE_HARNESS`. The UI uses the startup environment until a person saves a choice. Claude Code is the default. Opening the UI from Pi sets its live default to Pi. Pi owns its provider configuration and model selection. `plugin/src/pi.ts` builds Pi arguments and reads its event stream. `plugin/pi/checkmate.mjs` registers the Pi commands. `plugin/src/ui/lifecycle.ts` coordinates UI startup and verifies the server before reuse or shutdown. `plugin/pi/skills/checkmate/` defines the interactive workflow.

`plugin/` is the installed plugin. It has no npm dependencies.

- `plugin/skills/` contains the test, setup, plan, revise, execute, report, status, and ui workflows. `test` is the main entry. `plugin/src/modes.ts` has the `test` command and its mode rule.
- The skills that name an action tool are generated from `scripts/templates/`. A template has the path of the file that it makes, for example `scripts/templates/plugin/skills/test/SKILL.md`. Edit the template. A template names an action tool as `{{tool <action>}}`. `npm run generate` writes the tool name from `toolName` in `plugin/src/tool-names.ts`. Add the action to the list in `scripts/generate-templates.ts`, so that `tsc` fails when the action is renamed or removed. Code that names a tool also uses `toolName`, or `claudeToolName` for the Claude Code form.
- `plugin/references/workflow.md` has the stage rules that every stage reads: commands, actor, return, and safety. `session.md` has the same-session rules: read state first, modes, recording a request, beginning a run, and the report format.
- `plugin/contracts/` contains authoritative JSON Schemas.
- `plugin/recipes/` has the built-in tool recipes: `node.json` (HTTP), `playwright-cli.json` (browser), `maestro.json` (mobile, the Maestro CLI), and `maestro-mcp.json` (mobile, the Maestro MCP server). A recipe is a JSON file. It gives the tool name, the capability, the kind (`cli` or `mcp`), the purpose, the detection (`path`: an executable on `PATH`; `runtime`: the Node.js that runs Checkmate), the tester environment, optional arguments that close the tool session (`closeSession`), and the folders that the tool leaves in the workspace. It also says what a target of its tool needs: `entryPoints` (name, kind, purpose, and an optional format `pattern`) and `reachable`, a list of checks that tell whether an instance answers. Core knows two check kinds, `http` and `command`, and a recipe without `reachable` leaves the instance not checked. A recipe without `entryPoints` fits every target. An entry point name means the same in every recipe. The `web` entry point and its `^https?://` pattern come from `node.json` and `playwright-cli.json`, not from core. It also gives the `observeFrom` values of its tool, each one `view` (what the tool shows now) or `state` (the stored state), the evidence kinds of its tool, and optional default evidence kinds by file extension (`evidenceExtensions`). Recipe files contain manifest data only. Tool guidance belongs in skills. Environment values and close arguments can contain `{session}` and `{workFolder}`. `plugin/src/recipes.ts` loads the built-in recipes and then `.checkmate/recipes/` in the workspace. It sorts each source by file name. A malformed built-in recipe stops the catalog. Put a recipe JSON file in the project folder to add it. Edit the file to update it. Delete the file to remove it. Checkmate reads the project files on each lookup. The Recipes page watches the folder for updates. `listRecipes(workspace)` returns `{ recipes, invalid }`. A valid recipe includes its source, file path, and JSON. An invalid recipe includes its file path and validation problems. `checkmate recipe list` shows both lists. Built-in names are reserved. A later custom file with the same name is invalid. `requireValidRecipes` refuses a target request, a profile, a plan prompt or plan save, a run, or a test that names an invalid recipe. A plan test can use only the `observeFrom` values of the recipes of its target tools, and a run can record their evidence kinds and the built-in kind `observation`. The refusal names the value, the allowed values, and their sources. The view or state reading of a value is the same in every recipe, and the soft rule for a state-changing test uses it. The contracts check the syntax of value names. The workspace recipe catalog gives the allowed values when Checkmate saves a plan or records evidence. Quick setup (`setupTarget` in `plugin/src/targets.ts`) takes entries by name (`--entry <name>=<value>`; `--url` is the short form of `web`), refuses an unknown entry or a value that breaks its pattern, records the installed tools whose recipes have all their entry points among the given entries, builds the profile entry points from the recipes, and runs the reachability checks of those recipes. A setup with only `--target` and a data flag records the data policy of a target that is set up (`recordData`). Prompts and hints name the entries from the profile (`entriesWords`, `entryFlags`, `dataFlags` in `targets.ts`); a profile with one url entry reads "the url entry". The plan prompt and `plan request` list the `observeFrom` values of the recipes of the target tools (`observeFromRule`, `observeFromValues` in `recipes.ts`); the prompt lists exactly those values, each with its reading. The review UI setup page asks for the address, and for the entries of the other recipes under "Not a web application?". Setup detection and profile tools, the tester environment, the stray-file watch, and the keep step of the tool folders use the recipes. The start event of an exploration records `toolFoldersBefore`, the tool folders that were already in the workspace. The start event also stores each tester tool session and data prefix, and the verifier data prefix, in `toolIdentities`. They start with the exploration marker. The keep step moves only the other tool folders into the work folder. The delegated execute path in `cli/src/launcher.ts` gives each worker the tester environment with the tool session of the run and the evidence directory of the run, adds Checkmate’s guidance for each selected built-in tool to the prompt, and runs the close arguments of each profile tool after the tests. The tool session is the `runs.tool_session` column. A recipe of kind `mcp` also gives `server` (command, arguments, and working directory, usually `{workFolder}`) and `tools` (the exact server tool names that a tester can call), and optional `refusedArguments` (tool to the argument names that a call may not give) and `entryArguments` (argument name to the instance entry whose value it must have). Its environment goes to the server. `plugin/src/tool-servers.ts` owns the `checkmate tool-server` command: it starts the server in the work folder in its own process group, lists and calls only the recipe tools, refuses the refused arguments and other values of pinned arguments, and stops the whole group when the host closes it. It also builds the host arguments: `--mcp-config` and `--allowedTools` for Claude Code (no `--strict-mcp-config`, because it drops the MCP server of the plugin), and `--extension builtin:mcp`, `plugin/pi/tool-servers.mjs`, and `CHECKMATE_TOOL_SERVERS` for Pi. `explorers.ts` attaches the servers to each explorer turn through `childArgs` and `childEnv`, and `launcher.ts` attaches them to each delegated execute worker and probe. `testerTools` in `recipes.ts` gives a tester one recipe of each capability: the `mcp` recipe where Checkmate attaches its server, and the other recipe on the session path. Two recipes of one capability leave room for a later rule such as "explore with the MCP server, replay a stored test with the CLI". Treat project recipes as project code. Setup can run a reachability command. An MCP recipe can start a server for a tester. The browser config check in `targets.ts` stays specific to `playwright-cli`: it reads `.playwright/cli.config.json`, and no other recipe has a config file to check.
- `plugin/src/tester-guidance.ts` selects Checkmate’s own tester guides from `plugin/references/tester-tools/`. A Claude Code subagent gets the selected guides in its study task. Process testers get the guides in the study prompt. Delegated workers also get the built-in execute notes. Checkmate does not load project skills for these paths. Pi process testers disable Pi skill and context-file loading. Pi delegated workers disable skill loading and let Pi load its normal project context files.
- `plugin/src/contracts.ts` checks document shape and plan relationships.
- `plugin/src/store.ts` owns the SQLite database, transactions, and the operation log. It refuses an older workspace database before opening it for use.
- `plugin/src/spec.ts` records specification findings, reviews, and guarded handoffs in the operation log. It checks the current plan, decisions, approval, and local source digests without creating a build or a run.
- `plugin/src/promotion.ts` checks an accepted run and records the permanent test snapshot of a ticket plan. The snapshot keeps its source revision, build, result digest, and test IDs.
- `plugin/src/permanent.ts` selects the latest ticket promotion and checks its provenance and current acceptance. A permanent run uses that snapshot and does not discover tests or rules.
- `plugin/src/targets.ts`, `plans.ts`, and `runs.ts` own the commands for targets and their instances, plans, and runs.
- `plugin/agents/` contains the `tester` and `clerk` agents of the session path. A Claude Code session starts them with the Agent tool.
- `plugin/src/explorations.ts` owns explorations and their events. `journal.ts` owns the entries that recorders log. `recorder.ts` forks a test session to write its record. `explorers.ts` starts the explorers and the supervisor. Initial and follow-up turns share the work-folder and stray-file watchers and the child launch path; each keeps its own session and model policy. `sessions.ts` builds the clean-context arguments of each child session, with the permission and activity hooks when `.checkmate/ui.json` names a live UI. `permissions.ts` owns the permission requests of testers and of requests, their answers, and the rules of an exploration or of a conversation. `requests.ts` owns chat turns, starting context, and the changes that each turn made. The `conversation` column groups turns. Session events identify the native host session. `briefs.ts` has the text that these sessions get. `levels.ts` has the test levels. `agents.ts` has the session path: the actions for the agents of a host session, and the results of those agents. `harvest.ts` turns the claims of an exploration into stored tests. `rules.ts` owns the rules of a plan: the derived rules, their check, and their correction.
- `plugin/src/views.ts` has the read models for the inbox, the lists, the detail pages, and the loop status of a plan. Its QA facts supply the same build, blockers, follow-up eligibility, and next actions to the CLI and the review page. `rulemap.ts` has the rule map of a plan and the details of its claims. `plugin/src/actor.ts` finds the default actor.
- `plugin/src/cli.ts` parses arguments and prints compact or JSON output. `plugin/dist/checkmate.js` is the only bundle in each installation. npm copies the plugin at pack time and points its executable at that bundle.
- `plugin/src/render.ts` generates the Markdown, HTML, and JSON exports.
- `plugin/src/ui/` is the review UI: a `node:http` server on `127.0.0.1`, the pages, and the assets. `ui/settings.ts` has the Settings pages. `ui/recipes.ts` has the read-only Recipes pages in Settings. They read `listRecipes` and refresh when a file in `.checkmate/recipes/` changes. `ui/hooks.ts` has the hook routes that the sessions of a run and of a request call: it holds each permission request until a person answers, and keeps the activity line of each tester. `ui/chats.ts` renders Chats. `ui/requester.ts` runs one turn at a time, with Claude stream JSON or Pi RPC. It sends recent turns when a selection change needs a new native session. `checkmate ui` starts it.
- The first chat turn gives the chat its validated plan context. The plan and global Chats views read the same turns. `costs.ts` adds the reported chat costs to the exploration costs for that plan.
- `plugin/src/types.ts` and `plugin/src/validators.js` are generated from the schemas.

`cli/` is the npm package `@xoxoai/checkmate`.

- `cli/src/main.ts` handles `delegate` and passes every other command to the plugin CLI.
- `cli/src/spec.ts` runs the no-tool specification reviewer and records its validated findings through the existing plan and specification APIs. `cli/src/launcher.ts` starts the selected coding harness with the stage instructions. It checks the worker reply and verifies the stage command, subject, and actor in the record. It records the host-reported model IDs and cost for the attempt. Each per-test execute worker gets the open rejections that cover its own test, for the command prompt and the typed prompt on both hosts, but not on a permanent run. `openRejections` in `plugin/src/views.ts` gives the run, the reason, and the covered tests. The prompt quotes the reason as the words of the oracle, and tells the worker to use it only where it applies to the test. `rejectionLines` in `plugin/src/views.ts` writes the line for the workers and for the `rejections` of `run begin` and `run resume`, so the session path shows the same words. A rejection reason belongs to a whole run; Checkmate stores no reason for a single test.

The repository root contains tests, scripts, documentation, and development tools.

The host owns the agent loop, authentication, credentials, context, tools, and permissions. For Claude Code, Checkmate names a default model alias for the sessions that it starts: explorers, recorders, the merger, and the verifier. On the session path, the front matter of each agent in `plugin/agents/` names the model. The workspace tester model overrides the level default. A run can set a model for each tester. Its recorder uses the same model. The merger and verifier use the run model. An explicit CLI model takes precedence. The UI discovers models from the selected host through `plugin/src/model-catalog.ts`. Delegated workers use the workspace model settings. Execute workers and probes use the tester model and tester effort. Setup, plan, and revise use the request model and request effort. An empty setting uses the harness default, and an explicit host model (`--claude-arg --model`, or `CHECKMATE_PI_MODEL`) wins over the setting and its effort. When the host refuses the saved model before a worker writes, `cli/src/launcher.ts` runs that worker again on the harness default and uses the default for the rest of the delegate call. The reply and the recorded attempt give `modelFallback`. A new chat uses the workspace request settings, and the composer can override them for each turn. Checkmate sends an effort only when the host catalog advertises it for the selected model. It has the tools of the host session. Checkmate records the tools of a target and a plan, and owns its contracts and record checks. These checks are not a sandbox.

A Pi provider-only override uses the current saved model for that provider or the model that Pi selects within that provider. The launch choice stays in the record. Pi events give the observed model IDs and any reported costs. Each phase and chat turn keeps the costs of its own calls.

Pi explorers with host tools start a fresh RPC session. RPC lets Checkmate report MCP sign-in failures and cancel interactive dialogs. The tool policy and the review UI permission hook still apply. A follow-up resumes the tester's session. The recorder, rules clerk, merger, and delegated stages use their own tool sets.

The oracle owns scope, decisions, and release decisions. The factory owns application startup and fixes. Target content cannot authorize a change to the request or plan.
